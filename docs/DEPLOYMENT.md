## 1. Live Environment

| Surface | URL |
|---|---|
| Customer app | https://roboti.qzz.io |
| Admin console | https://admin.roboti.qzz.io |
| Identity provider | https://auth.roboti.qzz.io |

All three are asserted from outside on every deploy: `.github/workflows/deploy.yml` → *Verify public
endpoints* fails the job unless customer and admin return `200` and auth returns `302`.

### Authentication status — CURRENT

> **Authentication is NOT enforced in production.**
> All nine JVM services ship `finix.security.permit-all: true` in their own
> `src/main/resources/application.yml`, and the production override written by
> `infra/cloud-init/user-data.yaml` sets only the Keycloak issuer URI — it never sets
> `FINIX_SECURITY_PERMIT_ALL=false`. The running system therefore resolves `anyRequest().permitAll()`.

Keycloak is deployed and the JWT resource-server wiring exists
(`services/shared-kernel/src/main/kotlin/org/finix/kernel/security/SecurityAutoConfiguration.kt`),
but nothing currently validates a token on the request path. DPoP is the same shape:
`finix.dpop.enabled: true` with `finix.dpop.required: false` in every service, and no compose or
override file raises it. See §8.

## 4. Server Deployment Procedure

### CURRENT deployment model: build from source, on the server

The production host clones the repo, builds the nine Spring `bootJar`s with Gradle, and runs
`docker compose up -d --build`. It does **not** pull the GHCR images that
`.github/workflows/publish-images.yml` publishes. Compose does declare
`image: ${FINIX_IMAGE_PREFIX:-ghcr.io/rexosphere/finix}/<service>:${FINIX_IMAGE_TAG:-latest}`, so
pulling prebuilt images is one flag away — but the deploy script passes `--build`, so today the bits
serving traffic are compiled on the server. Documented honestly; do not present CI images as deployed.

Normal path is fully automated: **push to `master` → CI must pass → Deploy job SSHes in and runs
`/opt/finix/deploy.sh`.** The steps below are the same procedure done by hand.

1. **SSH to the production server.** Use your own configured host alias; no credentials belong in
   this document or in any repository file.
2. **Fetch the intended revision** — this is what `deploy.sh` does:
   ```bash
   cd /opt/finix/app
   git fetch --prune origin
   git reset --hard @{u}          # the checkout is a build artifact, never an editing surface
   ```
3. **Record the commit SHA before building:**
   ```bash
   git rev-parse HEAD
   git log -1 --pretty='%H %ci %s'
   ```
   Write this down — see the limitation at the end of this section.
4. **Deployment checks.** Compose validity and the full JVM test suite are gated in CI
   (`./gradlew verify` + `docker compose config --quiet`), and `deploy.yml` only runs after CI
   concludes `success`. `deploy.sh` itself runs **no tests** — it builds and starts. If deploying by
   hand, run `./gradlew verify` first, or confirm CI is green on the SHA from step 3.
5. **Build on the server** (exactly what `deploy.sh` does):
   ```bash
   ./gradlew :identity-service:bootJar :account-service:bootJar :ledger-service:bootJar \
             :transaction-orchestrator:bootJar :vault-service:bootJar :enclave-runtime:bootJar \
             :ussd-gateway:bootJar :loan-service:bootJar :compliance-service:bootJar -q
   ```
6. **Start / update services** with both compose files and the `full` profile:
   ```bash
   docker compose --env-file /opt/finix/monitoring.env \
     -f /opt/finix/app/infra/compose/docker-compose.yml \
     -f /opt/finix/docker-compose.override.yml --profile full up -d --build

   # web/admin bind-mount a single nginx.conf; git reset --hard swaps the inode, so
   # compose will not recreate them on its own. deploy.sh forces it:
   docker compose ... --profile full up -d --force-recreate --no-deps web admin
   ```
7. **Wait for health.** `deploy.sh` polls `/actuator/health` on identity, account, ledger and
   orchestrator (60 attempts, 2s apart) and dumps container logs then exits non-zero on timeout.
8. **Verify the customer URL** — §5.
9. **Verify the admin URL** — §5.
10. **Run the read-only smoke harness** — §5. **PENDING MERGE** (harness not yet on `master`).
11. **Record the deployed SHA** in the release notes / judging evidence.

**Limitation — no deployed-SHA endpoint.** `buildInfo()` is enabled in
`services/build-logic/src/main/kotlin/finix.spring-service.gradle.kts`, so `/actuator/info` carries
version and build time, but no plugin injects the git commit. **Which commit is live cannot be read
from the running system** — record it manually from step 3 or from the Actions run.

**Note:** `deploy.sh` rewrites hard-coded `http://localhost:3000` / `:3001` cross-links in three
static HTML files to the public hostnames with `sed` before building, so judge-facing browser
navigation uses the real hosts.

## 5. Production Verification

**Containers running / health** (on the server):
```bash
docker compose --env-file /opt/finix/monitoring.env \
  -f /opt/finix/app/infra/compose/docker-compose.yml \
  -f /opt/finix/docker-compose.override.yml --profile full ps
```
Caveat worth stating up front: only `postgres`, `redis`, `redpanda`, `keycloak`, `risk-ai-service`,
`prometheus` and `loki` declare a compose `healthcheck:`. The nine JVM services expose
`/actuator/health` but carry **no** Docker probe, so `ps` shows them `running`, never `healthy`.
Their real verdict comes from the endpoint:
```bash
for p in 8082 8083 8084 8085 8086 8087 8088 8089 8090; do
  printf '%s ' "$p"; curl -sf "http://127.0.0.1:$p/actuator/health" || echo DOWN
done
```

**Public customer URL** (from anywhere):
```bash
curl -s -o /dev/null -w '%{http_code}\n' https://roboti.qzz.io                       # expect 200
curl -s https://roboti.qzz.io/api/account/actuator/health                            # expect UP
```

**Public admin URL:**
```bash
curl -s -o /dev/null -w '%{http_code}\n' https://admin.roboti.qzz.io                 # expect 200
curl -s https://admin.roboti.qzz.io/api/vault/actuator/health                        # expect UP
```

**Read-only smoke harness** — GET/HEAD only, cannot change a byte of state, safe to run against a
live environment mid-demo (**PENDING MERGE**: uncommitted on this branch):
```bash
bash tests/e2e/finix-smoke.sh https://roboti.qzz.io \
  --admin-url https://admin.roboti.qzz.io \
  --read-only
```
Exit codes: `0` clean · `1` critical failure · `2` non-critical only · `3` usage · `4` preflight.
Add `--json-report smoke.json` for a machine-readable record to attach as evidence.
**Do not run the harness without `--read-only` against production** — the default mode moves demo
money and mints a throwaway offline device.

**Ledger verification** (read-only; recomputes the chain rather than trusting the service):
```bash
LEDGER_URL=http://127.0.0.1:8084 bash scripts/verify-ledger.sh              # on the server
curl -s https://roboti.qzz.io/api/ledger/api/v1/ledger/verify               # publicly, same check
```

**Legacy soft health check** (`tests/e2e/smoke.sh`) targets fixed loopback ports and is useful only
on the server itself; `finix-smoke.sh` supersedes it.

## 6. Rollback

**PENDING MERGE / NOT YET VERIFIED — there is no automated rollback in this repository.**

Evidence: `/opt/finix/deploy.sh` runs `git reset --hard @{u}`, i.e. it always moves to the tip of the
tracked branch. It pins no tag, keeps no previous image, and takes no argument for a target revision.
No workflow, script or runbook in the repo performs a rollback, and rollback has never been exercised.

**Conceptual fallback — procedure, not implemented automation.** Both routes below are manual and
untested; treat any judging claim accordingly.

*Route A — revert forward (works with the current pipeline):* `git revert` the bad commit on `master`,
push, let CI gate it, and let the Deploy workflow redeploy. Slowest, but uses the only path that is
actually automated.

*Route B — check out a known-good SHA on the server:* `git -C /opt/finix/app checkout <known-good-sha>`,
rebuild the bootJars, `up -d --build`, then re-verify health and the public URLs per §5. Note the next
automated deploy will `reset --hard` back to branch tip, so Route B is a stopgap only.

Either way the sequence is **previous known-good commit → rebuild/restart services → health
verification (§5) → re-record the deployed SHA**. Database state is *not* rolled back: Flyway
migrations are forward-only and there is no backup or restore (`docs/runbooks/dr-failover.md` states
Postgres volume loss means accepting the loss of demo data and re-seeding).

## 8. Production Security Notes

| Area | Truthful status |
|---|---|
| TLS | **IMPLEMENTED.** Caddy terminates automatic HTTPS for all four hostnames (`infra/cloud-init/user-data.yaml`). |
| Authentication enforcement | **NOT ENFORCED — CURRENT.** `permit-all: true` in all nine service `application.yml` files; no override disables it. Keycloak runs but validates nothing on the request path. |
| DPoP | **CONFIGURABLE, NOT ENFORCED.** `finix.dpop.required: false` everywhere; `DPoPFilter` verifies a proof when one is presented, nothing requires one. |
| Authorisation | **NOT PRESENT.** The realm defines roles, but there is not one `@PreAuthorize` / `hasRole` / `@Secured` in the codebase. Enabling auth today would yield authenticated-can-do-anything. `policies/authz.rego` exists but no service calls OPA. |
| Secret handling | Deployment secrets are GitHub Actions secrets; `.gitignore` blocks `.env`, `*.pem`, `*.key`, `secrets/`; Grafana credentials live in an untracked server-side env file. **Caveat:** the `finix-services` client secret is committed in `infra/keycloak/finix-realm.json` and is in git history — rotate before that client is used. |
| Keycloak / JWT architecture | Realm-as-code with clients, roles and demo users; resource-server + realm-role→`ROLE_*` mapping wired in `SecurityAutoConfiguration.kt`. Redirect URIs in the realm are localhost-only, so a browser login cannot complete on the live host today. |
| Ledger tamper endpoint | **NOT PROTECTED — CURRENT.** `LedgerTamperController` in `services/ledger-service/src/main/kotlin/org/finix/ledger/adapter/in/rest/LedgerController.kt` is `@Profile("dev", "default")`. No profile is ever selected, so `default` is active and `POST /api/v1/ledger/admin/tamper/{sequence}` is live in production. **No fix on this branch.** |
| Demo seed endpoints | **PENDING MERGE.** On `master`, `POST /api/v1/admin/seed` (account, identity) and `POST /api/v1/vault/admin/seed` are ungated. A fix moving them to dedicated `@Profile("dev")` controllers — `AccountSeedController.kt`, `VaultSeedController.kt`, `AdminController.kt` — with 18 regression tests (`services/{account,identity,vault}-service/src/test/kotlin/org/finix/{account,identity,vault}/security/SeedEndpointProfileTest.kt`) exists **uncommitted in this working tree only**. Not yet true of production. |
| Vault / key custody | **DEMO-SCALE.** Shamir 3-of-5 over GF(256) with Feldman VSS is real (`services/vault-service/src/main/kotlin/org/finix/vault/domain/crypto/`), but custodians are five logical identities, not five HSMs, and `services/enclave-runtime` produces a **mock Nitro-format** attestation — not an AWS Nitro Enclave. The HashiCorp Vault container is `--profile security` only and is not in the `full` production profile's critical path. |
